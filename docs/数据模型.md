# 数据模型

三张表，全部以 `owner_id` 归属用户，配合行级安全策略（RLS）实现数据隔离。

## 安全模型

| 机制 | 作用 |
|---|---|
| `owner_id TEXT NOT NULL DEFAULT auth.uid()` | 归属人由服务端根据登录态填充，客户端不发送 |
| RLS 策略（每表 4 条） | `SELECT` / `INSERT` / `UPDATE` / `DELETE` 都要求 `owner_id = auth.uid()` |
| `INSERT` 用 `WITH CHECK` | 插入的行必须满足 `owner_id = auth.uid()`，防止伪造归属 |
| `UPDATE` 同时用 `USING` + `WITH CHECK` | 防止把行的归属改成别人 |
| 表级 `GRANT` + 序列 `GRANT` | 缺少任一都会导致 `42501`（权限不足） |

客户端代码**从不发送 `owner_id`**，仅用于界面判断，不作为安全边界。

## profiles

一人一行（`owner_id` 唯一），保存身体数据与计算结果。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGINT` | 主键，自增 |
| `owner_id` | `TEXT` | 归属用户，默认取登录态 |
| `nickname` | `TEXT` | 昵称 |
| `gender` | `TEXT` | `male` / `female`，默认 `male` |
| `age` | `INTEGER` | 年龄 |
| `height_cm` | `NUMERIC(5,1)` | 身高（厘米） |
| `weight_kg` | `NUMERIC(5,1)` | 体重（公斤） |
| `activity` | `NUMERIC(4,3)` | 活动系数，默认 `1.55` |
| `goal` | `TEXT` | `lose` / `maintain` / `gain`，默认 `maintain` |
| `target_kcal` | `INTEGER` | 目标摄入热量 |
| `bmr` | `NUMERIC(7,1)` | 基础代谢 |
| `tdee` | `NUMERIC(7,1)` | 每日总消耗 |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | 时间戳 |

## food_logs

每日饮食记录，按 `log_date` 查询当天。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGINT` | 主键，自增 |
| `owner_id` | `TEXT` | 归属用户 |
| `log_date` | `DATE` | 记录日期，默认当天 |
| `name` | `TEXT` | 食物名称 |
| `grams` | `NUMERIC(7,1)` | 份量克重，默认 100 |
| `kcal` | `NUMERIC(8,1)` | 每 100g 热量 |
| `protein` / `fat` / `carb` | `NUMERIC(7,1)` | 每 100g 三大营养素 |
| `sodium` | `NUMERIC(8,1)` | 每 100g 钠含量，可空 |
| `source` | `TEXT` | 来源：`local`（内置库）/ `off`（在线查得） |
| `created_at` | `TIMESTAMPTZ` | 时间戳 |

索引：`(owner_id, log_date DESC)`，支撑「查当天记录」。

## custom_foods

用户自建食物库。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGINT` | 主键，自增 |
| `owner_id` | `TEXT` | 归属用户 |
| `name` | `TEXT` | 食物名称 |
| `kcal` | `NUMERIC(8,1)` | 每 100g 热量 |
| `protein` / `fat` / `carb` / `sodium` | `NUMERIC` | 每 100g 营养素 |
| `unit_name` | `TEXT` | 常见份量名（如「一片」） |
| `unit_grams` | `NUMERIC(7,1)` | 份量克重，默认 100 |
| `category` | `TEXT` | 分类，默认「自建」 |
| `image_path` | `TEXT` | 营养成分表照片的对象存储路径，可空 |
| `created_at` | `TIMESTAMPTZ` | 时间戳 |

索引：`(owner_id, created_at DESC)`。

## 对象存储

营养成分表照片存放路径：

```
users/<用户id>/labels/<随机id>.jpg
```

- 只有归属用户可读写删除
- 展示时用短时效签名链接（默认 600 秒，可选1–3600 秒）
- 删除食物条目时一并清理对应照片

## `body_metrics`（历史身体数据）

每日一条身体数据快照，用于生成长期体重与热量摄入趋势图。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGSERIAL` | 主键 |
| `owner_id` | `TEXT` | 归属用户，默认 `auth.uid()` |
| `metric_date` | `DATE` | 记录日期，默认当天 |
| `weight_kg` | `NUMERIC` | 体重（kg） |
| `height_cm` | `NUMERIC` | 身高（cm） |
| `bmr` | `NUMERIC` | 当日基础代谢（千卡） |
| `tdee` | `NUMERIC` | 当日总消耗（千卡） |
| `target_kcal` | `INTEGER` | 当日目标热量 |
| `note` | `TEXT` | 备注，可空 |
| `created_at` | `TIMESTAMPTZ` | 创建时间 |

- 唯一索引 `(owner_id, metric_date)`：同一天只保留一条，重复保存为覆盖更新
- 热量摄入趋势不落库，直接由 `food_logs` 按 `log_date` 聚合，避免两份数据不一致
- 与其它三张表一致：`owner_id` + RLS 行级安全，客户端不发送 `owner_id`

## 来源校验（Origin）

云服务数据平面精确校验请求的 `Origin` 头，只放行应用注册时绑定的发布域名。

| 请求来源 | 响应 |
|---|---|
| 官方发布域名 | `200` 放行 |
| 其它任意域名 | `403` `access_denied: the request origin is not allowed for this client` |
| 完全不带 `Origin` | `401` `invalid_grant` |

此外，签发的 access token 中 `azp` 字段绑定了官方发布域名，用于防止跨域盗用。

**结论**：应用无法部署到 GitHub Pages 等自有域名后继续使用云端功能。
这不是可通过配置解决的问题，而是服务端的安全策略。
